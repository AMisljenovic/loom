# v0.2.0 — Prompt layer as Loom's visible strength

This iteration takes Loom's prompt and instruction system from "competent"
to "the thing people remember." The infrastructure is largely in place —
mode-specific prompts, the stable/volatile split, rules autoload, skills
catalogue, sub-agent presets. The work below is craft: tightening,
unifying, and going one level deeper than competitors on the surfaces
users actually see.

This is not greenfield. Most tasks edit existing files. A few introduce
new conventions that the agent then has to thread through code.

## Where Loom already wins

Reading the current code: this is real prompt architecture, not the
single-string mush most agents ship with.

- ✅ Per-mode system prompts (`code`, `architect`, `ask`, `debug`) live
  in `agent/internal/prompts/*.md`, embedded via `embed.FS`
- ✅ Stable/volatile system prompt split for prompt caching, with the
  cache breakpoint placed deliberately
- ✅ Provider-aware rules autoload (`.loomrules`, `CLAUDE.md`+`.claude/rules/`
  for Anthropic, `AGENTS.md`+`.codex/rules/` for OpenAI)
- ✅ Skills catalogue advertised in the stable prefix; bodies injected on
  `load_skill` into volatile tail
- ✅ Sub-agent preset with its own focused prompt (`research.md`)
- ✅ Diagnostics feedback loop with `<diagnostics-followup>` synthetic
  user messages — already a sharp move competitors don't have

## Where it shows seams

Real problems, ordered by impact:

1. **Mode prompts are similar but uneven.** They share boilerplate
   ("Stream natural-language text directly to the user") and each
   reinvents how it describes the same tool. A consistent template would
   shrink them, make differences clearer, and reduce drift.
2. **Tool descriptions live in Go literals.** Each tool's `Description`
   is one English sentence inside `tools.go`, far from where the model
   actually reasons about it. Updating is awkward; consistency is hard.
3. **No house style for output.** The mode prompts each have an `# Output`
   section but they vary. There's no shared vocabulary for citations,
   diffs, code blocks, file paths.
4. **No prompt evaluation harness.** Changing a prompt is a guess. There's
   no way to know if a tweak made things better, worse, or both depending
   on the task.
5. **Sub-agent surface is thin.** One preset, one prompt, no documented
   "how the parent briefs the sub-agent" pattern. Roo's mode system has a
   richer story here.
6. **`.loomrules` exists in the rules loader but isn't documented for
   users.** Users who want to bring their own rules to Loom don't yet have
   a guide for the file format, precedence, or examples.
7. **Skills are advertised but underused.** Three skill files exist
   (`go-conventions`, `testing`, `vscode-api`). The pattern is sound but
   the library is sparse and the model isn't strongly prompted to load
   them at the right moments.
8. **Mode-switch language is loose.** "Acknowledge briefly — the extension
   may have already switched" gestures at a behavior but doesn't pin it
   down. Users will hit edge cases.
9. **No prompt versioning.** When you change `code.md`, there's no record
   of why. Behavior shifts silently across releases.

This list defines the v0.2.0 scope.

## Goals, in priority order

1. **Unify the prompt house style** so all modes feel like the same product
2. **Move tool descriptions out of Go code into Markdown** with a
   consistent template
3. **Establish output conventions** the model follows in every mode
4. **Build a minimal prompt evaluation harness** so changes are measurable
5. **Document `.loomrules` and project-instruction precedence** for users
6. **Expand and improve the skills library**
7. **Tighten sub-agent prompting** and the parent-to-sub-agent briefing
   pattern
8. **Add a prompt changelog** so behavior shifts are tracked

## Day 1 — Prompt architecture audit

**Goal:** Document the current prompt layer before changing it. Read your
own work with fresh eyes.

**Tasks:**
- Read all four mode prompts side by side. Note: duplicated phrases,
  inconsistent tool guidance, places where one mode says something useful
  the others don't.
- Trace one task end-to-end: a user prompt arrives, what does the LLM see?
  Construct the exact stable + volatile system prompt for a fresh `code`
  mode task, write it to `docs/prompt-snapshots/code-empty.txt`. Do the
  same for `architect`, `ask`, `debug`, and the `research` sub-agent.
- Snapshot the stable prefix byte-stable check: run the same conversation
  twice; diff the stable prefix. Should be zero diff.
- Identify three to five "this should be the same across modes but isn't"
  things. Identify three to five "this is specific to a mode and should
  stay specific" things.

**Definition of done:** Audit doc at `docs/v0.2.0/prompt-audit.md` listing
shared bones and per-mode flesh. Five snapshots saved. Stable-prefix
identity verified.

**Why first:** every following day touches something in here. Without the
snapshot baseline you can't tell if a "fix" later broke something else.

## Day 2 — Shared mode template

**Goal:** Every mode prompt follows the same skeleton. Differences are
intentional, not accidental.

**Tasks:**
- Define the canonical mode prompt template at
  `agent/internal/prompts/_template.md` (not loaded as a mode — purely
  documentation). Sections, in order:
  1. **Identity** — one short paragraph: who you are, where you run, what
     you're optimized for in this mode.
  2. **Constraints** — what tools you cannot use; what kinds of changes
     are off-limits in this mode.
  3. **Working style** — bullets describing the model's approach. Three
     to six bullets max.
  4. **Tool guidance** — when to reach for which tool *in this mode*. Not
     a tool catalogue (that's elsewhere). Mode-specific advice only.
  5. **Safety** — secrets, destructive commands, project rules autoload
     reminder. Same paragraph across modes.
  6. **Output** — formatting expectations specific to this mode. Mode-
     specific phrasing on top of the shared output rules (Day 4).
- Rewrite `code.md`, `architect.md`, `ask.md`, `debug.md`, and `research.md`
  against this template.
- Pull the duplicated "Safety" paragraph into a single canonical version
  used verbatim across modes.
- Move shared tool-guidance phrasing into the central tool descriptions
  (Day 3); keep only mode-specific tool advice in mode prompts.

**Definition of done:** All five mode prompts visibly share structure.
The "Safety" section is byte-identical across modes. Snapshots updated.
Re-run a representative task in each mode; behavior unchanged or improved.

**Watch for:** the temptation to compress prompts to "save tokens." Mode
prompts are part of the stable prefix and benefit from prompt caching;
they're roughly free on the second turn. Clarity beats brevity here.

## Day 3 — Tool descriptions as data files

**Goal:** Move tool descriptions out of Go string literals and into
Markdown files with consistent structure. The model gets richer guidance;
maintainers get a saner editing experience.

**Tasks:**
- Create `agent/internal/tools/descriptions/` with one Markdown file per
  tool: `read_file.md`, `apply_diff.md`, `run_command.md`, etc.
- Define a template (write it as `_template.md`):

  ```markdown
  ---
  name: apply_diff
  category: write
  requires_approval: true
  ---

  ## Purpose
  One sentence on what it does.

  ## When to use
  - Bullet
  - Bullet

  ## When NOT to use
  - Bullet
  - Bullet

  ## Input
  Describe each input field beyond what JSON Schema captures. Why does the
  model care about each one?

  ## Behavior
  Quirks the model needs to know. For apply_diff: oldText must be unique;
  followups come back as diagnostics.

  ## Examples
  Two or three minimal `<example>` blocks showing good usage.
  ```
- Add a Go loader (`agent/internal/tools/descriptions.go`) that reads the
  embedded Markdown files and exposes the structured description.
- The `Tool.Description` field becomes the file's `## Purpose` section so
  the existing tool catalogue stays compact. The richer description is
  injected into the stable prompt prefix under a new section: "Tool
  details (load with the tool name in mind):".

  Decision point: do you want the full descriptions always in prompt, or
  loadable on demand like skills? **Recommendation: always in prompt.**
  Tool details are far more frequently consulted than skills. The token
  cost is recovered by prompt caching.
- Update `code.md`, `debug.md`, etc. to remove duplicated tool guidance
  that now lives in the per-tool Markdown.

**Definition of done:** Every tool has a description file. Go literals
no longer contain English tool guidance (only the one-line Purpose).
Prompt prefix grew but is still byte-stable across turns. Sample tasks
in each mode behave the same or better.

**Watch for:** input schema duplication. Keep JSON Schema in Go, English
explanations in Markdown.

## Day 4 — Output conventions document

**Goal:** Define a house style for what the model produces, so it feels
like the same product across modes and tasks.

**Tasks:**
- Write `agent/internal/prompts/_output_conventions.md`. Sections:
  - **Citations.** When you reference a file, use a workspace-relative
    path. When you reference a line, use `path:line` or
    `path:start-end`. Never paste long file contents back at the user.
  - **Code blocks.** Use triple-backtick blocks with language tags. For
    diffs, show only the changed region with three lines of context
    unless asked.
  - **Lists and structure.** Use Markdown lists for >3 items. Use prose
    for ≤3 items. Use numbered lists only for sequenced steps.
  - **Brevity.** First sentence answers the question. Subsequent
    sentences add depth. No preamble ("Great question! Let me think...").
  - **Uncertainty.** If you don't know, say so. Don't speculate without
    flagging it.
  - **Confirmations.** After completing a task, end with a one-line
    summary: files changed, tests run, next step.
- Inject this section into the *stable* prefix between mode prompt and
  tool catalogue. It's identical across modes (and across most tasks)
  so it caches well.
- Strip mode-specific output guidance that duplicates this. Mode prompts
  keep only mode-specific output (e.g. architect's "numbered steps,
  trade-offs, open questions").

**Definition of done:** Every mode references the shared conventions
implicitly (because they're in the prefix). Outputs across modes feel
more coherent. Snapshots updated.

**Watch for:** over-specification. Output conventions should fit on one
screen. Anything longer is a sign you're prescribing too much.

## Day 5 — Prompt evaluation harness

**Goal:** Make prompt changes measurable instead of vibes-based.

**Tasks:**
- Create `agent/internal/eval/` (new package). Define:
  - `Scenario` — a struct: name, mode, initial workspace files, user
    prompt, expected behaviors (a list of assertions like "called
    `read_file` with X", "produced a diff touching file Y", "did not call
    `apply_diff`").
  - `Runner` — runs a scenario against a real LLM provider (or recorded
    fixtures), captures the full transcript, checks assertions.
- Build the first ten scenarios. Distribution:
  - 3 Code mode: simple edit, multi-file refactor, "write a test"
  - 2 Architect mode: design plan, refactor proposal
  - 2 Ask mode: code explanation, "where is X handled"
  - 2 Debug mode: failing test, runtime error
  - 1 Research sub-agent: focused investigation
- Add `npm run eval` (calls `go run ./agent/cmd/eval`). Runs all scenarios
  against the configured provider with a tight token budget per scenario.
  Outputs pass/fail and timings.
- Important: scenarios are *not* deterministic. The harness scores
  behavior, not exact strings. A scenario "passes" when its assertions
  hold; minor stylistic variation is fine.

**Definition of done:** `npm run eval` runs locally. All ten scenarios
pass on the current prompts. The harness is documented in a new
`agent/internal/eval/README.md`.

**Watch for:** scope creep into "an LLM benchmark." This is a regression
suite for prompt changes, not a research project. Ten scenarios is plenty
for v0.2.0.

## Day 6 — `.loomrules` documentation and examples

**Goal:** Users can bring their own rules to Loom and know exactly how.

**Tasks:**
- Write `docs/loomrules.md`. Cover:
  - File format (Markdown, no required structure)
  - Precedence (`.loomrules` always; provider-specific files based on
    `llm.Provider.Family()`)
  - The 32 KB cap and what happens beyond it (`<truncated: N files
    omitted>` marker)
  - The provider rule files Loom recognizes (`CLAUDE.md` +
    `.claude/rules/*.md`, `AGENTS.md` + `.codex/rules/*.md`)
  - The bundle envelope (`<rules sources="...">`) the model sees
  - How rules interact with mode prompts (mode prompt sets baseline,
    rules layer on top)
- Ship three example `.loomrules` files in `examples/loomrules/`:
  - `monorepo.md` — rules for a multi-package repo
  - `legacy-codebase.md` — rules for an old codebase with weird patterns
  - `strict-tests.md` — rules enforcing test coverage and TDD
- Add a section to `README.md` linking to `docs/loomrules.md`.

**Definition of done:** A user could read `docs/loomrules.md` and write
their own `.loomrules` correctly. Examples demonstrate the patterns.

**Watch for:** over-promising. `.loomrules` is text that goes into the
system prompt; it can't enforce behavior, only nudge it. Say so.

## Day 7 — Skills library expansion

**Goal:** Make skills genuinely useful by having more of them, and by
teaching the model when to load them.

**Tasks:**
- Audit current skills (`go-conventions`, `testing`, `vscode-api`). Keep
  them; tighten if needed.
- Add new built-in skills, each in `agent/internal/skills/builtin/`:
  - `react-conventions` — function components, hooks, no class
    components, VS Code CSS variables for theming
  - `typescript-strict` — patterns for strict mode, `unknown` over `any`,
    type narrowing
  - `error-handling` — language-agnostic error handling patterns: don't
    swallow, wrap with context, don't log-and-return
  - `git-workflow` — conventional commits, one concern per PR, when to
    rebase vs merge
  - `performance-investigation` — how to approach a perf issue: measure
    first, profile, hypothesize, test
- For each skill, follow a tighter template:
  ```markdown
  ---
  id: <id>
  synopsis: <one sentence, appears in catalogue>
  triggers: [list, of, topics, that, suggest, loading]
  ---

  <body, max 800 words>
  ```
- Update `code.md` and `debug.md` working-style sections to include:
  > "Before working in an area covered by a skill (Go conventions,
  > React/TS, testing, error handling, performance), call `load_skill`
  > with the relevant ids. Skill bodies persist for the rest of the
  > conversation."
- Add an eval scenario: "ask the model to write Go code that needs error
  handling; verify it called `load_skill('go-conventions', 'error-handling')`
  first." Probabilistic, but if it passes 4/5 times, behavior is right.

**Definition of done:** Eight built-in skills. Model loads them at the
right moments (verified via eval scenario). Synopses in the catalogue
clearly indicate the skill's scope.

**Watch for:** writing skills that overlap. Each skill should be the
canonical place for its topic, not just one of three places where you
mention testing.

## Day 8 — Sub-agent briefing pattern

**Goal:** Parent agents brief sub-agents well. Sub-agents return summaries
parents can use.

**Tasks:**
- Update the `code.md` and `architect.md` sections that describe
  `spawn_subagent`. Be explicit about the contract:
  > "When spawning a research sub-agent, your `context` field must
  > include: (1) what the parent is trying to accomplish, (2) what you
  > already know from this conversation that the sub-agent shouldn't
  > re-derive, (3) what specifically the sub-agent should find and
  > return. The sub-agent has zero memory of this conversation; its
  > context is its only inheritance."
- Update `research.md` to be explicit about the return contract:
  > "Your summary is the only artifact the parent sees. Structure it
  > with: (1) the direct answer in 2–3 sentences, (2) evidence with file
  > paths and line numbers, (3) anything you couldn't verify."
- Add an eval scenario where two sub-agents are needed for a real task
  (e.g. "find all auth logic" + "find all session logic"). Verify the
  parent's `context` fields are non-trivial (not just the user prompt
  repeated) and the summaries are structured.
- Document the briefing pattern in `SUBAGENTS.md` under a new section,
  "Briefing Sub-Agents."

**Definition of done:** Parent agents reliably brief sub-agents with
useful context. Sub-agent summaries reliably follow the three-part
structure. Eval scenario passes.

**Watch for:** the parent dumping its entire conversation history into
`context`. The briefing should be focused, not exhaustive. Add explicit
prompt guidance discouraging dumps.

## Day 10 — Dogfood, tighten, ship

**Goal:** Use it on real work for a day. Tighten what's awkward. Ship.

**Tasks:**
- Three real tasks in each mode (12 total). Pay attention to:
  - Does the mode feel distinct from neighboring modes?
  - Do tool descriptions read smoothly when the model uses them?
  - Do skills load at the right moments?
  - Are outputs consistent with the conventions doc?
  - Does sub-agent briefing happen well?
- For each issue: small fix or backlog. Don't expand scope.
- Re-run `npm run eval`. Confirm no regression.
- Update `ROADMAP.md` to reflect v0.2.0 done; preview v0.2.1 (the natural
  follow-ups, see "Out of scope" below).
- Bump version in `package.json` and Go binary metadata. Tag and release.

**Definition of done:** v0.2.0 released. Eval suite green. Real dogfooded
sessions feel measurably more coherent than v0.1.4.

## Out of scope for v0.2.0

These are tempting but belong to later iterations.

- **User-defined custom modes** beyond the four built-ins. Currently
  modes are TS-defined (`src/modes.ts`); making them user-defined needs
  a settings UI and validation. Plan for v0.3.0.
- **More sub-agent types.** Right now `research` is enough. `refactor`
  and `test_runner` come when the v1.1 sub-agent infrastructure is
  battle-tested.
- **Multi-language skill auto-detection.** "When user opens a Python
  file, load Python conventions skill automatically." Nice idea, but
  requires the indexer to surface language stats and is a deeper
  change. v0.3.0.
- **Per-conversation prompt overrides.** "For this chat only, use these
  rules." UX-heavy, easy to misuse.
- **Prompt A/B testing against real users.** That's a v1.x feature.
- **Localization of prompts.** English-only for v0.2.0.

## Risk register

**Tool descriptions in Markdown bloat the stable prefix.** Possible.
Mitigation: enforce per-tool length cap (say, 400 words) and review at
end of Day 3. Prompt caching protects per-turn cost; first-turn cost
goes up by ~30%. Acceptable.

**Eval harness becomes a maintenance burden.** Real risk. Mitigation:
ten scenarios cap; running takes a few minutes; updating scenarios is
required only when behavior contracts change, not when prompts shift
stylistically.

**Mode prompts start to feel "corporate" once unified.** Counterintuitive
but real — too much consistency erases personality. Mitigation: review
mode prompts at end of Day 2 for distinctive voice. If `architect`
sounds like `code` sounds like `debug`, push back.

**Skills don't load even with prompting.** Models vary. Mitigation: eval
scenario tracks load rate. If under 50% on the right scenarios, write
more aggressive prompt language or move to programmatic auto-load
(later iteration).

**Tool descriptions in Markdown drift from JSON Schema.** The schema is
truth for validation; English description is truth for guidance.
Mitigation: Day 3 task includes a check that loads each description
file and validates the front-matter `name` matches a registered tool.
Fail loudly if mismatched.

**Sub-agent briefing pattern doesn't transfer.** Parent agents stay lazy.
Mitigation: prompt language alone may be insufficient; if the eval
scenario fails repeatedly, consider injecting briefing examples directly
into the parent's tool-use guidance for `spawn_subagent`.

## What "done" looks like

- All five mode prompts visibly share structure but read distinctly
- Tool descriptions live in versioned Markdown with consistent structure
- Output conventions are shared across modes and the model follows them
- Eight built-in skills, loaded when relevant
- `.loomrules` is documented; example files ship
- Sub-agent briefing is structured; sub-agent summaries are structured
- `npm run eval` runs ten scenarios; all pass
- `docs/prompt-changelog.md` records the work
- Three days of real dogfooding produced no surprises that blocked release
